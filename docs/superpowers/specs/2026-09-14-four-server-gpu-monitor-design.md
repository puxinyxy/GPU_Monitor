# GPU Monitor 四服务器扩展设计

日期：2026-09-14  
状态：设计已批准并实施；远端兼容修复待最终实机复验

## 1. 目标

在不改变现有轮询、占用判断和通知语义的前提下，将 GPU Monitor 从两台服务器扩展到四台。原有两台 3090 服务器的地址和端口保持不变，新增两台各 8 卡 A100 的服务器。升级必须兼容已经存在的 `servers.json`，不得保存服务器密码，也不得引入开机自启、远程终端或进程控制能力。

## 2. 服务器清单与显示顺序

新建配置以及当前标准两服务器配置迁移后，菜单按以下固定顺序显示：

| ID | 显示名称 | 主机 | SSH 端口 | 用户名 |
| --- | --- | --- | ---: | --- |
| `server-10122` | `3090 · 10122` | `122.207.108.8` | `10122` | `yanxiaoyang` |
| `server-10165` | `3090 · 10165` | `122.207.108.7` | `10165` | `yanxiaoyang` |
| `server-a100-18200` | `A100 · 18200` | `js2.blockelite.cn` | `18200` | `yanxiaoyang` |
| `server-a100-13000` | `A100 · 13000` | `js2.blockelite.cn` | `13000` | `yanxiaoyang` |

两个新端点当前均能解析到地址并建立 TCP 连接。DNS 解析结果不写入配置，运行时始终使用主机名，以免未来地址变化导致配置失效。

## 3. 配置与无损迁移

`ConfigurationStore` 的新建配置包含上述四条记录。读取已有配置时按以下顺序执行一次幂等迁移：

1. 保留既有的 `server-10165` 旧地址纠正逻辑：仅将精确匹配 `122.207.108.8:10165` 的旧记录迁移为 `122.207.108.7:10165`。
2. 仅当原服务器记录的 ID、地址、端口和旧数字标签均精确匹配时，将 `10122`、`10165` 标签分别更新为 `3090 · 10122`、`3090 · 10165`。用户自定义标签不被覆盖。
3. 对每台新 A100 服务器：若配置中既不存在相同 ID，也不存在相同主机名和端口，则按批准顺序把记录追加到末尾。若用户已用自定义 ID 配置同一端点，则保留该记录且不制造重复轮询。
4. 保留所有其他自定义记录、相对顺序、用户名和密钥路径；菜单始终遵循最终配置数组顺序。若批准 ID 已被不同端点占用且目标 A100 端点尚不存在，则保留用户记录，并用第一个未占用的确定性回退 ID（`原批准 ID-migrated`，必要时追加递增数字后缀）添加目标端点，确保不会静默漏机。后续启动先按主机名和端口识别该端点，因此迁移保持幂等。
5. 只有数据实际变化时才以原子写入方式更新 `servers.json`；再次启动不得重复添加或反复重写。

当前安装的两服务器配置符合自动迁移条件，因此新版应用首次启动后会得到四条记录，无需保存或嵌入密码。

## 4. 轮询和状态处理

现有 `MonitorCoordinator` 已按配置数组并发轮询服务器，扩展后继续复用该机制：

- 每 15 秒对四台服务器各执行一次独立 SSH 探针。
- 任一服务器失败只更新该服务器的 health，不阻塞或隐藏其他服务器的成功快照。
- GPU 是否空闲仍只由计算进程是否存在决定；利用率、显存和温度只用于展示。
- 首次采样、双次确认、离线三次确认、恢复通知以及最后成功快照保留规则不变。
- 菜单栏汇总标题统计四台服务器的全部已确认 GPU。

## 5. 菜单布局

两台新 A100 服务器会新增 16 行 GPU 数据，叠加原服务器后会超过常见屏幕高度。服务器区改为有最大高度的垂直滚动区域，通知状态、上次更新时间、立即刷新和退出按钮放在滚动区域之外并保持可见。

本次不增加折叠状态、搜索、服务器编辑器或分页。服务器标题直接显示配置中的 `3090 · 端口`、`A100 · 端口`，GPU 行的指标和进程展示保持不变。

## 6. SSH 配置与安全边界

`scripts/provision_ssh.sh` 的批准端点扩展为四个明确的主机/端口对，不使用主机与端口的笛卡尔组合。四台服务器共用现有专用 Ed25519 身份，但每个主机/端口在专用 `known_hosts` 中独立固定。

远端仍只安装同一条受限 `authorized_keys` 记录：禁止 Agent、X11、端口转发、PTY 和用户 rc，并强制执行固定的只读 `nvidia-smi` 查询。每个 GPU 与 compute-app 查询先调用绝对路径 `/usr/bin/nvidia-smi`，仅在首次调用精确返回 `127` 时，才通过固定 `/lib64/ld-linux-x86-64.so.2` 对同一二进制和同一组固定参数重试；其他非零状态以及 loader 自身失败保持可见。固定命令不读取 `SSH_ORIGINAL_COMMAND` 或任何用户输入，两条查询仍只通过 marker 和 `&&` 串联。

这是对验收时观察到的远端运行时兼容问题的窄处理：2026-09-14 在 `js2.blockelite.cn:13000` 观察到 `nvidia-smi` 文件可执行但其 ELF 默认 interpreter 路径不可用，而固定 loader 能执行同一只读查询。该事实只描述当次验收环境，不假定端点未来一直保持同一状态；运行时是否 fallback 完全由每次首次调用的精确退出状态决定。

脚本继续验证：

- 返回格式包含唯一 marker 和至少一条合法 GPU 行；
- 请求其他命令时仍只能得到强制监控输出；
- 显式端口转发被拒绝；
- 新安装条目若后续验证失败，只回滚本轮增加的精确行；从唯一 exact legacy 行迁移的条目则恢复该 exact legacy 行；原本就是新精确行时不回滚。

对相同可信 key blob，只允许唯一、逐字节精确匹配的旧受限行经同目录 `0600` 临时文件原子替换为新行；弱限制、未知行或重复 blob 失败关闭。迁移或新增后的 forced-command、forwarding、final validation 任一失败都会走与来源对应的原子恢复/删除操作，恢复失败仍失败关闭并只输出净化后的人工修复指引。登录密码仅由系统 `ssh` 在交互式终端读取，不进入参数、环境变量、源码、配置、日志、测试夹具或应用包。重新运行脚本对已存在的新精确受限 key 保持幂等。

## 7. 错误处理

- TCP、认证、主机密钥、远端命令和解析失败继续使用现有分类。
- 新服务器失败不会改变原服务器地址或密钥配置。
- 主机密钥不匹配时失败关闭，不自动删除或替换 `known_hosts`。
- 配置迁移写入失败时保留原文件，不返回半写入数据。
- 应用替换继续使用现有 staging、签名校验、备份和恢复流程；失败不得留下损坏的 `/Applications/GPU Monitor.app`。

## 8. 测试策略

实施采用 TDD，先增加失败测试，再修改生产代码：

1. 新建配置精确包含四台服务器及批准顺序、标签、主机和端口。
2. 既有两服务器配置迁移后得到四台，原服务器端点不变、数字标签升级、A100 记录追加。
3. 迁移保持幂等，并保留用户自定义标签、同端点自定义记录、其他服务器和密钥路径；批准 ID 被其他端点占用时仍以稳定回退 ID 添加目标 A100，且不会重复添加。
4. provisioning 策略测试逐一验证四个明确端点；行为测试验证每次 SSH 调用的 destination、端口和专用 `known_hosts` 参数没有串配。
5. AppModel 测试覆盖新 A100 GPU 从忙到空闲、从空闲到占用时沿用现有双次确认并触发对应 macOS 通知，且单台失败不影响其他三台状态。
6. 视图测试与运行态验收共同确认服务器列表可滚动、footer 始终位于滚动区之外且可操作；现有显示映射测试继续通过。
7. Core、App、provisioning、installer、packaging 全套测试以及 Swift 严格并发、warnings-as-errors 构建全部通过。

## 9. 实机验收

完成代码后按以下标准验收：

1. 为两个新端点交互式安装并验证受限公钥；原两端点继续使用原地址和端口。
2. 使用与应用完全相同的 SSH 参数对四个端点采样；完整实机验收要求四个端点全部连通且输出通过生产解析规则。
3. `js2.blockelite.cn:18200` 与 `js2.blockelite.cn:13000` 各返回恰好 8 张 GPU，GPU 名称包含 A100；不输出完整远端进程详情到验收日志。
4. 重装并启动固定路径 `/Applications/GPU Monitor.app`，确认只有一个 GPU Monitor 运行进程。
5. 观察应用自身轮询子进程，确认四个主机/端口配对均被实际访问，且不存在旧的错误端点或主机/端口串配。
6. 展开菜单并实际滚动服务器列表，确认所有服务器和 GPU 行可达，同时 footer 中的通知状态、更新时间、立即刷新和退出按钮始终可见并可操作。
7. live `servers.json` 包含四条期望记录且不含 password 字段；专用 `known_hosts` 能分别查到四个端点。
8. 安装包签名有效，安装版与 `dist` 主程序哈希一致，无安装事务残留，也不新增开机自启。

若任一服务器当时因外部网络或服务器状态不可达，必须如实报告该端点的 connectivity 状态，并将“四服务器实机验收”标记为未完成；不得把外部故障误报成代码失败，也不得因此隐藏另外三台的结果。

## 10. 不在本次范围内

- 微信通知实现；只保留现有预留边界。
- 开机自启。
- GPU 历史数据持久化。
- 远程 Shell、任务停止或进程控制。
- 图形化服务器增删改界面。
- 自动接受变化后的 SSH 主机密钥。
